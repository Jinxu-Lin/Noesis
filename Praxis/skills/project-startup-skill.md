# Skill: Project Startup (研究项目启动)

## 触发场景
研究者希望启动一个新的研究项目，需要 AI 理解相关背景材料并建立结构化的知识基础。

## 输入
研究者提供以下任意组合：
- 论文 PDF / arXiv 链接 / 论文内容
- 领域描述 / 关键词
- 研究者自己的初步想法或直觉
- 已有的笔记或草稿

## 执行流程

### Step 0: 框架同步 + 项目初始化

**0a. 同步 ResearchFlow 框架**（确保使用最新方法论）:
```bash
cd [ResearchFlow路径] && git pull origin main
```
如果有更新，通知用户：框架已更新，本次使用最新版本。

**0b. 创建项目目录结构**（新项目）:

```bash
mkdir -p [项目名]
cd [项目名]
# 自动化运行器所需目录
mkdir -p phase-outcomes
```

创建以下初始文件结构：

```
[项目名]/
├── CLAUDE.md                  ← 本步骤创建（见下方格式）
├── phase-outcomes/            ← fork agent 写入 outcome JSON
├── contribution.md            ← Phase 2 时填写，现在可先创建空文件
└── pipeline-evolution-log.md  ← 各阶段反思记录，现在可先创建空文件
```

**Phase 8 时会新增**：`Code/` 目录及 `code-todo.md`、`experiment-todo.md`
**Phase 9 时会新增**：`Papers/` 目录

**0c. 创建 CLAUDE.md**（项目入口文件）:

### Step 1: 研究种子定位与核心假设提取

**1a. 识别研究种子类型**

根据研究者提供的信息，判断属于哪种类型：
- 方法融合型（多个方法结合）
- 方法延伸型（改进已有方法）
- 领域迁移型（方法迁移到新领域）
- 问题驱动型（从问题出发）
- 现象启发型（从观察出发）
- 混合型（以上多种的组合）

**1b. 显性化核心假设**

研究者的直觉背后隐含着一系列前提假设——在阅读源材料之前，先把这些假设写成清单并标注：

| 假设 | 来源 | 当前支撑强度 |
|------|------|------------|
| 假设描述 | 研究者推断 / 源材料名称 | 强（有直接证据）/ 弱（间接推断）/ 无（待验证） |

**要求**：至少提取 3 条假设。每条必须是"如果为假则整个方向站不住脚"的关键命题，不能是无关紧要的细节。

---

### Step 2: 深度理解源材料

对每份源材料执行：
1. **阅读与理解** — 全面理解材料内容
2. **结构化提取** — 提取核心方法、关键贡献、技术细节
3. **正向关联标注** — 标注与研究者洞察相关的支持性证据
4. **反向标注** — 标注源材料中与 Step 1 假设相矛盾、构成挑战、或暗示边界条件的内容（哪怕是轻微的信号）

要点：
- 不要泛泛总结，要聚焦于与研究种子相关的技术细节
- 保留数学公式和关键定义的精确表述
- 如果是论文，重点关注方法论部分，而非实验结果
- **反向标注不是为了否定方向，而是为 Step 4 的压力测试积累原材料**

---

### Step 3: 知识综合与 Gap 分析

1. 分析源材料之间的**关系图谱**（互补/竞争/正交）
2. 识别现有工作的**空白地带**
3. 评估研究者洞察的**技术可行性**（定性判断）
4. 识别潜在的**技术风险**

本步骤产出"**第一版研究方向**"，作为 Step 4 的检验对象。
在本步骤不必追求完美——有瑕疵的第一版比过度打磨更好，因为 Step 4 会暴露真实问题。

---

### Step 4: 三帽压力测试（多视角种子检验）

> 本步骤借鉴 Sibyl System 的多视角辩论机制，以"单 Agent 换帽"方式执行。
> 目标：对 Step 3 产出的研究方向施加结构化压力，在进入 P2 之前发现盲点。

**执行规则**：依次带三顶帽子，每顶帽子独立完成分析后再换下一顶。禁止"戴着后一顶帽子软化前一顶的质疑"——每顶帽子的结论必须基于独立判断。

每条质疑必须**引用 Step 1-3 中的具体材料或发现**，禁止抽象概括（如"可行性需要进一步评估"这类空话视为无效输出）。

---

#### 帽子 A：质疑者（Contrarian 视角）

> 角色：严格的魔鬼代言人，系统性挑战主流假设。寻找盲点、隐藏失败模式、被忽视的反面证据。目标不是否定，而是让活下来的想法更强。

提问框架：
1. Step 1 列出的假设中，哪些在源材料里找不到实质支撑？这意味着什么风险？
2. "如果研究者的核心洞察恰好是错的"——源材料中有没有任何证据支持相反的结论？
3. 如果这个方向在 P8 实验中失败，最可能的根本原因是什么？（给出 1-2 个具体场景）

输出格式：
```
[质疑者分析]：150-300字
⚠️ [具体质疑1]
⚠️ [具体质疑2]
⚠️ [具体质疑3（如有）]
```

---

#### 帽子 B：工程师（Pragmatist 视角）

> 角色：务实的 ML 工程师，只相信能在有限算力下验证的想法。关注资源约束和工程现实。

提问框架：
1. 实现最小 pilot（≤1 GPU-day）需要哪些工程组件？有现成实现的是哪些，需要从头开发的是哪些？
2. 从启动到得到第一个有意义的实验结果，最保守估计需要多长时间、多少算力？
3. 有没有"工程陷阱"——看起来简单但实际上需要大量工程工作的环节？

输出格式（必须给出具体数字/组件，不能模糊）：
```
[工程师分析]：100-200字
✓ [组件A] — 有现成实现（如：HuggingFace transformers）
✗ [组件B] — 需从头开发，估计工作量 X 天
? [组件C] — 不确定，需调研
⏱️ 最保守估计：[时间] / [算力]
```

---

#### 帽子 C：实验家（Empiricist 视角）

> 角色：严谨的实验科学家，深信不可证伪的命题没有科学价值。每个实验设计都要经得起同行审查。

提问框架：
1. 什么样的实验结果会**迫使**放弃这个方向？（否证条件：给出具体数字线或现象）
2. 最小可验证实验（1 GPU-hour 量级）的核心测量是什么？能提供早期信号吗？
3. 当前方向是否存在容易与成功信号混淆的 confounders？如何控制？

输出格式：
```
[实验家分析]：100-200字
❌ 否证条件：如果[具体实验结果/数字]，则该方向不成立
🔬 最小pilot：[具体实验设计，1-2句]
⚡ 关键confounder：[名称] — 控制方法：[具体做法]
```

---

#### 检验综合

在三帽分析之后，执行决策：

| 情形 | 判定 | 处理 |
|------|------|------|
| 三帽均无严重问题 | **方向确认** | 保持 Step 3 方向，注明三帽已通过 |
| 某帽发现可处理问题 | **方向修正** | 记录修正了什么、为什么这样修正 |
| 某帽发现根本性质疑 | **方向调整** | 提出修改后的方向，解释如何解决该质疑 |
| 多帽发现相互强化的严重问题 | **HIGH RISK** | 标记风险等级，提示研究者在 P2 前重新评估 |

---

### Step 5: 生成 Startup 文档

按照 `templates/project-startup.md` 模板，生成完整的项目启动文档。

**Step 4 的三帽检验结果以完整形式纳入文档**（不压缩、不删减），作为后续阶段的参考基线。

要求：
- 源材料总结要**深入而精准**，有技术深度，而非浅层概述
- Gap 分析要**具体而尖锐**，指出确切的技术缺口
- 研究方向要与 Gap 直接对应，形成逻辑闭环
- **方向描述反映三帽检验后的最终版本**（如有修正，注明修正了什么及原因）

---

### Step 6: 与研究者确认

将文档呈现给研究者，确认：
- 对源材料的理解是否准确？
- Gap 分析是否命中要害？
- 三帽检验发现的问题，研究者是否认可？是否有需要补充的上下文来消解质疑？
- 否证条件（实验家帽提出的）是否符合预期？

如果研究者对某顶帽子的质疑有异议，记录异议和理由，纳入文档的"检验综合"部分。

## 输出
一份结构化的 `project-startup.md` 文档，包含：
- 项目知识基础（源材料深度解读）
- 知识综合与 Gap 分析
- **三帽压力测试结果**（已检验的假设清单 + 三视角分析 + 方向综合）
- 研究方向（经过压力测试后的确认/修正版本）

## 质量标准
- 技术深度：能体现对方法论的深层理解，而非表面总结
- 结构清晰：后续阶段可直接引用本文档的特定章节
- 逻辑闭环：从源材料 → Gap → 三帽检验 → 修正方向，形成自然推导链
- **检验有效性**：每顶帽子至少提出 1 条可被当场验证或反驳的具体质疑
- 可操作性：读完文档后，AI 应能独立理解项目的技术语境和已知风险

## 注意事项
- 研究者的核心洞察是起点，AI 的角色是帮助**显性化、结构化并压力测试**，而非替代研究者的创造性判断
- 不要急于提出方法细节，startup 阶段的目标是建立共识 + 发现盲点，不是设计方案
- **三帽检验是善意的压力测试，不是否定研究者**——经过检验仍能站住脚的方向反而更有信心进入 P2
- 如果三帽检验发现了研究者明显不知道的根本性问题，应当诚实指出，即使研究者可能不想听
- P2（Gap Discovery）将在本文档基础上深入分析——三帽检验中未解决的质疑会自动成为 P2 的重点

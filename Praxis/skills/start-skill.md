# Skill: Project Start（研究项目启动）

## 核心定位

`Start` 阶段的本质不是写论文草稿，而是做一次 **research charter / 立项判断**。

你的职责只有一个：

> 判断这个研究方向是否值得从 0 到 1 开始。

这里的"值得开始"至少包含五个问题：

1. 这是不是一个真实存在的问题？
2. 这个问题为什么重要，而不是"看起来有意思"？
3. 现有工作为什么还没有解决它？
4. 我们现在是否已经看到一个可信的突破口？
5. 如果这个直觉是错的，能否尽快发现？

你需要和研究者一起完成的，不是提前写完 `Gap / Method / Experiment`，而是把研究种子整理成一个足够清楚、足够诚实、足够可否证的起点。

---

## 不是什么

`Start` 不应退化成以下任何一种东西：

- 缩写版论文
- 空泛愿景文档
- 完整方法设计文档
- 完整实验设计文档
- 大而全的文献综述

出现以下信号时，应主动收回来：

- 如果内容已经在定义完整的技术路线、模块拆解、公式推导，说明写得太靠后了
- 如果内容已经在枚举 benchmark、指标、ablation 和统计 protocol，说明越界到了 `Experiment`
- 如果内容只剩"这个方向很重要"，但说不清问题对象和失败条件，说明还没有形成可立项的研究对象

---

## 执行原则

### 1. 先研究对象，后研究手段

先回答"问题到底是什么"，再讨论"可能怎么做"。
如果研究者上来就给方法，先追问它试图解决的真实问题是什么。

在 DL 领域，这个原则尤其重要：很多项目的失败源于"先有了一个 fancy 的技术手段，再去找它能解决的问题"。一个常见的陷阱是研究者被某个新架构或新技术（如 Mamba、MoE、Flow Matching）吸引，然后试图把它嫁接到一个并不真正需要它的任务上。好的研究起点应该是"我观察到了一个真实的性能瓶颈或理论缺陷"，而不是"我想用 X 技术"。

### 2. 只做支持立项判断的阅读

阅读源材料时，不追求面面俱到，只提取对以下问题有帮助的信息：

- 这个问题是否真实
- 这个问题是否重要
- 现有方法为什么失效或不足
- 哪些证据支持这个方向继续看
- 哪些信号提示这个方向可能不成立

除非某个数学定义本身决定了方向是否成立，否则不要在 `Start` 阶段做过深的公式展开。

### 3. 只给出 tentative bet，不给出完整解法

允许写：

> 我们怀疑关键结构是 X，因此一个可能的切入点是 Y。

不允许写成：

> 我们的方法由 A、B、C 三个模块构成，并将在 D、E、F 上验证。

### 4. 风险与否证必须和热情同时出现

成熟的 `Start` 文档必须同时回答：

- 最大风险是什么
- 哪条关键假设一旦为假，方向就应收缩或停止
- 哪种最小证据足以支持进入下一阶段

### 5. 严守因果顺序

遵循：

`Start -> Gap -> Method -> Experiment`

`Start` 可以看到后面阶段的轮廓，但不能替后面阶段写草稿。

## 执行流程

### Step 1：明确研究种子与问题对象

先把研究者当前的直觉压缩成一张"研究种子卡"：

- **研究种子一句话**：这个方向到底在试图理解什么
- **种子来源**：方法融合型 / 方法延伸型 / 领域迁移型 / 问题驱动型 / 现象启发型 / 混合型
- **问题对象**：具体什么现象、机制、任务或假设没有被正确表述
- **受影响对象**：如果这个问题持续未解，会误导谁、限制什么、卡住哪一类工作

如果来源于 Episteme，记录对应知识资产，保留可追溯性，但不要机械复述知识库内容。

本步骤的目标不是"把想法说漂亮"，而是把研究对象说准确。

#### DL 领域中好的研究种子的特征

一个值得追求的 DL 研究种子通常具备以下特征，缺一则需要警惕：

**解决真实瓶颈，而非假想问题**：
- 好种子："Transformer 在长序列上的 attention 是 O(n^2)，限制了 context window 扩展" — 这是被大量实践验证的真实瓶颈
- 坏种子："现有 attention 不够优雅" — "优雅"不是可衡量的瓶颈
- 判断方法：能否指出具体的任务/数据集/场景中，因为这个瓶颈导致了可量化的性能损失？

**有明确的技术路径（至少有一条候选路径）**：
- 种子阶段不需要完整方法，但需要至少一个"为什么这条路可能走通"的直觉
- 例如："注意力模式在长文本中表现出稀疏性（已有观测证据），这暗示可以用稀疏近似来降低复杂度"
- 如果连候选路径都看不到，说明种子还不成熟

**有可衡量的改进目标**：
- 不是"更好"，而是"在 X 任务上把 Y 指标从 A 提高到 B"
- DL 领域的常见度量维度：accuracy/F1（效果）、FLOPs/latency/throughput（效率）、参数量/内存占用（规模）、泛化性（OOD 表现）、样本效率（数据量需求）

**区分五种种子来源的要点**：
- **方法融合型**（"把 A 领域的技术用到 B 问题上"）：最大风险是两个领域的隐含假设不兼容，需要追问"A 技术依赖什么前提，B 问题是否满足"
- **方法延伸型**（"在现有方法 X 上做改进"）：最大风险是改进空间已被挤压（diminishing returns），需要看 X 的性能曲线是否已经平台期化
- **领域迁移型**（"把成功范式迁移到新领域"）：最大风险是新领域的数据特性不支持迁移假设，如 NLP 的 pretrain-finetune 范式迁移到时间序列是否合理
- **问题驱动型**（"观察到一个真实问题"）：最稳健的种子类型，但风险在于问题可能已经被近期工作解决
- **现象启发型**（"观察到一个有趣的实验现象"）：风险在于现象可能是 artifact 而非真实信号，需要追问实验设置是否干净

### Step 2：显性化核心假设

把研究者直觉背后的关键前提写成假设表。

要求：

- 提取 **3-5 条** 核心假设
- 每一条都必须是"如果为假，整个方向会明显受损"的命题
- 区分哪些已有支撑，哪些只是猜测

建议格式：

| # | 核心假设 | 来源 | 当前支撑强度 | 若为假会怎样 |
|---|----------|------|--------------|--------------|
| 1 |  | 研究者判断 / 源材料 | 强 / 弱 / 无 |  |

不要把"可以调参改善"这类次要问题写进假设表。

#### DL 研究中常见的隐含假设类型

研究者的直觉往往建立在多层隐含假设之上，而这些假设很少被明确检验。以下是 DL 研究中最常见的四类隐含假设，每类都需要被显性化并写入假设表：

**数据假设**（最容易被忽略，也最致命）：
- "训练数据中存在足够的 X 模式供模型学习" — 例如假设代码数据中包含足够的逻辑推理样本
- "数据分布是 i.i.d. / 平稳的 / 有某种结构" — 例如假设用户行为数据是平稳分布的
- "数据标注质量足以支撑监督信号" — 例如假设 human preference 标注是一致的
- "数据规模足以让方法生效" — 很多方法在小数据上失效，但论文只在大数据上报告结果

**模型假设**（关于表示能力和归纳偏置）：
- "模型架构具有足够的表示能力来捕获 X" — 例如假设 Transformer 能学到长距离依赖
- "引入的归纳偏置与任务结构一致" — 例如假设图结构对分子属性预测是必要的
- "模型规模/容量足以容纳目标知识" — 例如假设 7B 模型能做复杂推理
- "预训练模型中已包含可迁移的相关知识" — 例如假设 ImageNet 预训练对医疗图像有用

**优化假设**（关于训练过程）：
- "损失函数的梯度信号足以指导学习" — 例如 reward model 的信号是否足够细粒度
- "训练过程能收敛到一个足够好的局部最优" — 例如 GAN 训练的稳定性假设
- "多个损失项之间不会严重冲突" — 多任务学习中的常见问题
- "超参数搜索空间是合理的" — 例如假设 learning rate warmup 的 schedule 对结果不敏感

**评估假设**（最容易导致虚假的"成功"）：
- "选用的 metric 能反映真实目标" — 例如 BLEU 是否真的衡量了翻译质量
- "benchmark 数据集代表了真实分布" — 例如 MMLU 是否代表了真实推理能力
- "baseline 是公平的" — 例如是否给了 baseline 足够的调参预算
- "改进是统计显著的" — 例如在小数据集上 0.5% 的提升是否有意义

**如何将模糊假设精确化为可证伪的陈述**：

模糊假设 → 精确假设的转换模式：
- "X 应该有帮助" → "在任务 T 上，加入 X 后 metric M 提升不低于 δ"
- "模型能学到 Y" → "在 probing 实验中，Z 层的表征对 Y 的线性可分性 > 阈值"
- "A 方法比 B 方法好" → "在固定计算预算 C 下，A 在数据集 D 上的 metric M 优于 B 至少 ε"

### Step 3：选择性读取源材料，做立项导向的证据整理

只读取对当前立项判断真正必要的材料。

对每份源材料，重点提取四类信息：

1. **支持信号**：它为什么让这个方向看起来值得继续
2. **反证信号**：它哪里直接挑战了核心假设
3. **边界条件**：它暗示了什么前提、限制或适用范围
4. **未解原因**：现有工作为什么还没有解决这个问题

输出时不要做"大而全总结"，而要把材料压缩成与立项相关的判断。

建议每份材料只回答：

- 它给这个项目增加了什么信心？
- 它暴露了什么危险？
- 它告诉我们"空白为什么存在"？

如果材料来自 Episteme，优先复用现有笔记，但仍要重新组织成面向本项目判断的证据。

#### 如何高效地判断一篇论文的价值

经验丰富的研究者不会从头到尾线性阅读一篇论文。以下是面向立项判断的高效阅读策略：

**阅读顺序（不是 Abstract → Introduction → Method → Experiment，而是）**：
1. **先看实验结果表格和图**：这篇论文最终实现了什么？数字有多强？在什么条件下？这决定了它是否值得继续读
2. **再看 Ablation Study**：哪些组件真正有贡献？经常发现核心贡献来自一个简单的 trick 而非宣称的主方法
3. **然后看 Limitation / Discussion**：作者自己承认的问题往往是最真实的，也可能正是我们要解决的 Gap
4. **最后才看 Method 细节**：只有当实验数据和 ablation 表明这篇论文确实有价值时，才值得深入理解方法

**高价值信号**：
- Ablation 中某个组件去掉后性能大幅下降 → 说明该组件确实关键，值得研究其原理或改进
- 不同数据集/任务上表现差异大 → 暗示方法有强假设，可能存在改进空间
- 作者在 limitation 中指出的 failure case → 直接的 Gap 来源
- "Surprisingly, X does not help" → 反直觉结果往往是深层问题的线索

**警惕信号**：
- 只在一个小数据集上有提升，没有大规模验证 → 可能是过拟合实验设置
- 没有 ablation 或 ablation 显示所有组件贡献相当 → 方法可能过度设计
- 实验设置与先前工作不一致（不同的 split、不同的预处理）→ 数字可能不可比
- 大量的超参数但没有 sensitivity analysis → 结果可能对调参高度敏感

### Step 4：形成第一版立项判断

在此步骤，不写论文式 `Crystallize`，而是回答五个立项问题：

1. **问题真实性**：这到底是不是一个真实问题？
2. **问题重要性**：不解决会持续造成什么后果？
3. **空白来源**：现有工作为什么没解决？
4. **突破口可信度**：当前最可信的切入点是什么？
5. **快速否证路径**：什么小规模观察足以说明它不值得继续？

本步骤的产物应是一个 **第一版 research charter**，而不是"第一版方法设计"。

建议把判断写成以下结构：

- **Why this is worth starting**
- **What we still do not know**
- **What could kill this direction quickly**
- **What would justify entering C**

#### DL 领域的 Go/No-Go 判断标准

经验丰富的研究者在做立项判断时会追问以下具体问题。任何一条的负面回答都应该触发慎重考虑：

**应该 Hold 的信号**（信息不足，需要先补证据）：
- 没有找到任何先前工作尝试过类似方向 → 可能是我们遗漏了文献，也可能确实是处女地，但需要确认"为什么没人做过"是因为"没想到"还是"试过但行不通"
- 核心假设的支撑完全来自直觉，没有任何实验证据 → 至少需要一个 toy experiment 或先前工作中的间接证据
- 所需计算资源超出可获取范围，且无法设计降规模的验证方案 → 例如需要 1000 GPU-hours 的预训练实验但只有 1 张 A100
- 关键的数据集/benchmark 不可获取或不存在 → 需要先确认评估方案的可行性

**应该 Stop 的信号**（方向本身有硬伤）：
- 近三个月内有顶会论文已经用类似方法解决了同一问题，且效果很强 → 除非有本质不同的角度，否则 novelty 不足
- 问题的根因分析指向了一个不可改变的物理/数学约束 → 例如信息论下界证明了某种精度-效率 trade-off 是不可突破的
- 所有候选切入点都依赖同一个脆弱假设，且该假设没有任何支撑 → 多条路径同时失败的风险太高
- "问题"实际上是"特定实现的缺陷"而非"方法论的缺陷" → 改进实现就能解决，不需要新研究
- 目标 metric 的提升空间已经很小（如 SOTA 已达 99.5%），且没有新维度（效率、泛化性等）可以作为贡献

### Step 5：多 Agent 并行多维度辩论（核心压力测试）

保留 **多 Agent 并行多维度辩论** 作为 `Start` 阶段的核心机制。

但要始终记住：这场辩论服务于 **立项判断**，不是为了提前完成论文展开。
每个 Agent 讨论的对象都应是 **research charter**：

- 问题是否真实
- 问题是否重要
- 空白为什么存在
- 当前突破口是否可信
- 哪些信号会杀死这个方向

任何 Agent 都不应把输出扩张成完整方法设计、完整实验设计或长篇综述。

#### 5a. 准备辩论上下文

整理以下内容，作为所有辩论 Agent 的共享输入：

```text
## 研究种子卡
[Step 1 产出]

## 核心假设清单
[Step 2 产出，含"若为假会怎样"]

## 立项导向证据整理
[Step 3 产出：支持信号 / 反证信号 / 边界条件 / 未解原因]

## 第一版立项判断
[Step 4 产出：为什么值得开始 / 还不知道什么 / 什么会快速杀死方向 / 什么足以进入 C]

project_path: <project_path>
debate_output_path: <project_path>/phase-outcomes/debate/<role>.md
```

创建输出目录：

```bash
mkdir -p <project_path>/phase-outcomes/debate
```

#### 5b. 并行召唤六个辩论 Agent

在单条消息中并行发起以下 6 个 Agent：

| Agent | Subagent 文件 | 在 `Start` 阶段的核心职责 |
|-------|--------------|--------------------------|
| 创新者（Innovator） | `innovator-subagent.md` | 判断这个方向是否真的打开了新空间，还是只是旧元素重组 |
| 务实者（Pragmatist） | `pragmatist-subagent.md` | 判断这个方向会最先卡死在哪个现实约束上 |
| 理论家（Theorist） | `theorist-subagent.md` | 判断问题定义是否成立、核心假设是否自洽 |
| 反对者（Contrarian） | `contrarian-subagent.md` | 构造最强反方论证，检验这是否可能是伪问题或伪突破 |
| 跨学科者（Interdisciplinary） | `interdisciplinary-subagent.md` | 判断是否存在更好的问题表述或来自外部领域的启发 |
| 实验主义者（Empiricist） | `empiricist-subagent.md` | 给出最小正面信号与最小否证条件 |

每个 Agent 的输出都必须回答以下五项，保持短而硬：

1. **最强继续理由**：为什么这个方向可能值得开始
2. **最危险失败点**：这个方向最可能死在哪里
3. **被施压的核心假设**：哪一条假设最脆弱
4. **关键证据要求**：还缺哪一条最关键的证据
5. **本视角建议**：`Go / Go with focus / Hold / Stop`

如果 Agent 输出开始滑向完整方法、公式细化或 benchmark 规划，应主动截断并收回到立项判断。

#### 六个辩论者在 DL 研究中应追问的核心问题

**创新者（Innovator）** 应追问：
- 这是一个真正新的问题框架，还是在旧框架上换了新术语？（例如："对比学习"只是换了名字的 metric learning？）
- 如果这个方向成功，会改变领域内其他人的做事方式吗？还是只多了一个可选方案？
- 与领域近期的趋势（如 scaling law、foundation model、test-time compute）是协同还是逆行？逆行不一定不好，但需要更强的理由

**务实者（Pragmatist）** 应追问：
- 方法的计算开销是否在可接受范围内？（DL 研究中，一个需要 8xA100 训练一周的方法如果只能用 1xA100，可能根本无法完成实验）
- 是否需要特殊的数据标注/收集？成本和时间估计是多少？
- 复现的难度如何？如果核心组件依赖精巧的工程 trick（如特定的 learning rate schedule、gradient clipping 策略），那么方法的鲁棒性值得怀疑
- 从现在到投稿 deadline 还有多长时间？方法的复杂度是否匹配时间窗口？

**理论家（Theorist）** 应追问：
- 问题定义中是否有循环论证？（例如："我们的方法更好因为它在我们设计的 metric 上更高"）
- 核心假设是否与已知的理论结果矛盾？（例如 No Free Lunch 定理、信息论下界）
- 方法的每个组件是否都有因果关系论证，还是只有"试了有效"的相关性？
- 如果方法有理论保证，保证的前提条件在实际中是否成立？

**反对者（Contrarian）** 应追问：
- "更简单的 baseline 是否就够了？"（DL 领域最致命的攻击。如果一个精心设计的方法只比调了参的 baseline 好 0.3%，那方法的 novelty claim 就站不住）
- 改进是否只来自增加了参数/计算？（如果 FLOPs-matched comparison 后优势消失，方法就没有真正的贡献）
- 类似的 idea 是否已经在其他名字下被尝试过了？（DL 领域的"重新发明轮子"非常常见）
- 如果 SOTA 再提升 5%，这个问题是否还存在？（判断问题是否是暂时性的）

**跨学科者（Interdisciplinary）** 应追问：
- 其他领域（信号处理、统计学、控制论、认知科学）是否有更成熟的解决方案？
- 问题的本质是否可以被重新表述为一个已解决的问题？（例如：attention 本质上是 kernel method，很多 efficient attention 方法可以从这个角度理解）
- 是否有跨模态/跨任务的迁移机会被忽略了？

**实验主义者（Empiricist）** 应追问：
- 最小验证实验（探针/probe experiment）是什么？需要多少时间和资源？
- 什么结果算"正面信号"，什么结果算"否证"？要有具体的数字阈值（例如："如果 Dim 0 的 accuracy 不超过 random baseline 的 2 倍，则方向不成立"）
- 是否存在可以快速执行的 toy experiment 来验证核心假设？（例如：在合成数据上测试，或者用现有模型的 intermediate representation 做 probing）
- 实验结果的可解释性如何？如果方法有效但我们不知道为什么有效，这对方向判断意味着什么？

#### 5c. 召唤综合者 Agent

六个辩论 Agent 完成后，顺序召唤综合者 Agent，读取：

- 第一版立项判断
- 核心假设清单
- `phase-outcomes/debate/` 下的六个角色输出

综合者必须产出：

- 最终结论：`Go / Go with focus / Hold / Stop`
- 值得启动的核心理由
- 必须优先处理的 3 个问题
- 进入 C 时必须带着的风险
- 哪条假设最值得先验证
- 六方意见中仍未消解的真实分歧

综合者的职责是"形成可执行的立项结论"，不是"平均采纳所有观点"。

#### 5d. 将综合结果呈现给研究者

向研究者呈现：

- 综合判定结果
- 六个视角中最重要的支持与反对理由
- 必须处理的优先问题
- 若继续推进，需要带入 C 的风险清单

如果研究者对某个视角有异议，记录异议与理由，但不要抹平分歧。
真实分歧本身就是 `Start` 阶段的重要产出。

---

### Step 6：输出 Startup 文档

按照 `Praxis/templates/project-start.md` 生成 `<project_path>/project-startup.md`，但必须按 `Start` 的职责来填写，而不是被模板牵着越界。

填写时遵守以下约束：

- `Research Seed`：讲清方向和核心矛盾，不讲方法细节
- `Source Materials`：写与立项判断相关的核心证据，不写全面综述
- `Knowledge Synthesis`：强调问题真实性、重要性、空白来源、风险
- `Stress Test`：保留多 Agent 辩论的综合结论、关键分歧和 kill criteria
- `Research Direction`：只写粗粒度方向与待澄清问题，不写完整技术路线

如果模板中的某个小节天然容易诱导越界，主动用以下方式收束：

- 把"研究问题"写成粗粒度研究问题，而不是精细 RQ 列表
- 把"拟议方法概述"写成 candidate idea，而不是方法蓝图
- 把"风险"写具体，把"计划"写克制

六个 Agent 的原始输出建议保存在 `phase-outcomes/debate/` 中，`project-startup.md` 只写：

- 综合判定
- 每个视角最有信息量的 1-2 条洞见
- 仍未解决的关键分歧
- 明确的 kill criteria

不要把六份长文机械拼接进主文档，否则会削弱 `Start` 文档作为立项基线的可读性。

---

### Step 7：与研究者确认立项结论

向研究者确认的重点不是"文档写得全不全"，而是以下四件事：

- 我们是不是在讨论同一个问题对象？
- 这个方向为什么值得开始，理由是否足够硬
- 当前最可信的突破口到底是什么
- 哪些结果一旦出现，我们就应该收缩、转向或停止

最后给出明确结论，四选一即可：

- **Go**：值得进入 C
- **Go with focus**：值得进入 C，但必须带着明确风险清单
- **Hold**：信息不足，先补关键证据
- **Stop**：当前不值得继续投入

如果研究者不同意某个压力测试结论，记录异议和理由，但不要为了"达成一致"而抹掉真实分歧。

---

### Step 8：只有在结论为 Go / Go with focus 时才初始化项目

如果方向通过立项判断，再执行项目初始化：

```bash
mkdir -p ~/Research/<project_name>/phase-outcomes
```

按 `Praxis/templates/project-claude-md.md` 创建 `CLAUDE.md`，并写入：

- `Noesis 路径`: `~/Research/Noesis`
- `当前阶段`: Phase 1 (Project Startup)

然后生成 `project-startup.md`，必要时创建：

- `research/contribution.md`
- `pipeline-evolution-log.md`

Git 初始化与 GitHub 仓库创建是**可选收尾动作**，不是 `Start` 阶段的核心目标。

如果研究者暂时不希望创建远端仓库，可以只做本地初始化，或者完全推迟到后续阶段。

最后推进状态机到 C：

```bash
python3 ~/Research/Noesis/Praxis/orchestrator/research_state_machine.py init-phase ~/Research/<project_name> C
```

并写入 `phase-outcomes/startup.json`。

如果结论为 `Hold` 或 `Stop`，不要强行初始化项目；此时更重要的是把"不启动的理由"写清楚。

---

## 输出

产出应包含两层结果：

### 1. 面向研究者的立项结论

- 方向判断：`Go / Go with focus / Hold / Stop`
- 值得投入的核心理由
- 当前最大的风险
- 最小否证条件
- 进入 C 前最该补的一个关键问题

### 2. 面向项目系统的 Startup 文档

`project-startup.md` 应成为后续 `Crystallize` 阶段的起点，其价值在于：

- 说明为什么开始
- 说明现在还不知道什么
- 说明为什么现有工作没有解决
- 说明什么结果会让我们停止自我说服

而不是提前替 `problem-statement.md`、`method-design.md`、`experiment-design.md` 写内容。

## 质量标准

- **问题清晰**：读完后能明确说出项目到底在试图理解什么
- **理由扎实**：能够解释为什么这个问题值得开始，而不是只会说"很重要"
- **突破口克制**：存在 candidate idea，但没有越界成完整方法设计
- **风险诚实**：关键风险、脆弱假设和 kill criteria 写得具体
- **辩论有效**：多 Agent 并行辩论确实增加了视角张力，而不是重复说同一件事
- **边界清楚**：`Start` 只负责立项，不偷写 `Gap / Method / Experiment`
- **可交接性**：后续阶段可以直接继承这里的假设、风险与开放问题
- **DL 特异性**：假设表中包含了数据/模型/优化/评估四类假设的审视，风险分析具体到了计算资源和时间窗口

---

## 注意事项

- 研究者的洞察是起点，AI 的职责是帮助显性化、校准和压力测试，不是替代研究者做创造性判断
- 不要因为材料很多，就自动把 `Start` 做成大型文献综述
- 不要因为研究者很兴奋，就回避坏消息；如果方向存在明显硬伤，应明确指出
- 不要因为模板里有槽位，就把每个槽位都写满；宁可克制，也不要越界
- `Start` 的成功标准不是"像一篇论文"，而是"让团队知道为什么值得开始，以及下一步最该先验证什么"
- 在 DL 领域，警惕"techno-optimism"（技术乐观主义）——不要因为一个技术"很酷"就认为它值得研究；始终回到"它解决了什么真实的、可衡量的问题"

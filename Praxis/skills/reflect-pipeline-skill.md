# Skill: Reflect Pipeline (流程反思) — 跨阶段通用

## 触发场景
任何 Work Phase 或 Review Phase 的 Skill 执行完成后，主动调用本 Skill 进行流程反思。

**注意**：本 Skill 产出的是**观察笔记**，不直接修改 pipeline.md 或其他 Skills。正式的流程进化在 Phase 11 Retrospective 中执行。

## 输入
- 刚完成的 Phase 编号和 Skill 名称
- 刚完成的 Phase 产出文档
- `pipeline.md`（当前版本）
- 刚执行的 Skill 文件内容
- `pipeline-evolution-log.md`（如已存在，读取已有观察，避免重复）

## 执行流程

### Step 1: 回顾刚完成的 Phase

带着批判性视角回顾刚才的执行过程，思考以下问题：

**关于 pipeline.md 中该 Phase 的描述**：
- 描述是否准确反映了实际执行中需要做的事？
- 有没有实际执行中很重要、但 pipeline.md 没提到的步骤或注意事项？
- 有没有 pipeline.md 强调了、但实际执行中发现不太重要或不太适用的内容？
- Exit Criteria 是否合理？有没有遗漏的关键检查点？有没有过于严格或过于宽松的标准？

**关于 Skill 文件**：
- 执行流程是否顺畅？有没有步骤顺序不合理的地方？
- 有没有执行中需要额外判断、但 Skill 没覆盖到的情况？
- 输入判断是否完备？有没有遗漏的执行模式？
- 输出是否完整？有没有实际需要但模板没涵盖的内容？

**关于跨 Phase 的流转**：
- 本 Phase 的输入文档质量如何？上游 Phase 是否提供了足够的信息？
- 本 Phase 的产出是否为下游 Phase 提供了充分的信息？
- Phase 之间的衔接是否顺畅？有没有信息断层？

### Step 2: 分类观察

将观察分为四类：

| 类别 | 含义 | 示例 |
|------|------|------|
| **缺失 (Missing)** | 流程中缺少的、应该有的内容 | "Phase 4 应该增加对计算复杂度的早期评估" |
| **冗余 (Redundant)** | 流程中有但实际不需要或效果不佳的内容 | "Gap 评估矩阵中的'可解决性'维度与根因分析重复" |
| **改进 (Improve)** | 现有内容可以做得更好 | "Dim 0 的通过标准描述可以更具体" |
| **确认 (Confirm)** | 流程中的好实践，值得保留和强调 | "组件级审查确实帮助发现了更好的替代方案" |

### Step 3: 评估改进优先级

对每条 Missing / Redundant / Improve 类观察评估：

| 维度 | 问题 |
|------|------|
| **影响范围** | 影响单个 Phase 还是多个 Phase？ |
| **置信度** | 这是一个项目的个例，还是可能是普遍性问题？（低/中/高） |
| **改进成本** | 修改 pipeline.md / skill 的工作量？ |

**关键原则**：置信度为"低"的观察仍然值得记录——多个项目的低置信度观察如果指向同一方向，综合起来就是高置信度。

### Step 4: 写入 pipeline-evolution-log.md

按以下格式追加一条 Entry 到 `pipeline-evolution-log.md`：

```markdown
## Entry [序号] — [Phase X: Phase名称] — [日期]

**项目**: [项目名称]
**执行的 Skill**: [skill 名称]
**执行模式**: [首次 / 迭代-来源]

### 观察

#### 缺失 (Missing)
- [ ] **[影响范围] [置信度]** — 观察描述
  - 建议改进：...

#### 冗余 (Redundant)
- [ ] **[影响范围] [置信度]** — 观察描述
  - 建议改进：...

#### 改进 (Improve)
- [ ] **[影响范围] [置信度]** — 观察描述
  - 建议改进：...

#### 确认 (Confirm)
- **Confirm** — 观察描述（什么做法有效，为什么）
```

**格式说明**：
- 每条观察前的 `[ ]` 是检查框，在 Phase 11 综合进化时标记已处理
- 影响范围：`[Phase X]` 或 `[跨Phase]` 或 `[Skill: xxx]`
- 置信度：`[低]` / `[中]` / `[高]`

## AI Co-Author 关键行为
- **诚实且具体**——不要泛泛而谈"流程可以更好"，要指出具体哪里、怎么改
- **区分个例和模式**——一个项目的一次执行可能有特殊性，标注置信度
- **不过度反思**——每次反思控制在 3-7 条观察，不必面面俱到
- **累积视角**——如果 pipeline-evolution-log.md 中已有类似观察，引用之前的 Entry 编号，说明是重复出现还是新角度
- **同时记录好的实践**——Confirm 类观察同样重要，避免进化过程中误删好的设计

## 输出
- `pipeline-evolution-log.md`（追加 Entry）

## 注意
- 本 Skill **不修改** pipeline.md、其他 Skill 文件或模板
- 正式的流程修改在 Phase 11 Retrospective 中的"Pipeline 进化"步骤统一执行
- 如果发现紧急的、明确错误的内容（如公式错误、流程矛盾），可以在 Entry 中标注 `[URGENT]`，提示用户立即审阅

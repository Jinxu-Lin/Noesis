# 探针实验执行指南（Probe Guide）

> 本文档是给研究者（人类）的执行指南，不是 AI Agent prompt。

## 核心目标

用**最小成本**验证核心直觉是否有经验信号。

## 探针实验的设计哲学

探针不是"跑一下看看"，也不是缩小版的完整实验。探针是一个精心设计的**信息获取实验**，其核心目标是：**以最小的时间和计算成本，最大化对"方向是否正确"的信息量。**

一个好的探针实验应该满足：
- **高信噪比**：结果能清晰区分"方向对"和"方向错"，而非产出模糊的信号
- **快速失败**：如果方向错了，应该能在小时级别（而非天级别）内暴露
- **诊断能力**：失败时能告诉你**为什么错**，而不只是"错了"
- **信息不对称**：即使 fail，获取的知识也足以指导下一步决策

## 重要提醒

1. **探针不是缩小版的完整实验** — 它验证的是**核心假设**，不是方法效果
2. **严格遵守时间预算** — `research/problem-statement.md` §3.4 定义的小时数
3. **即使 fail 也要记录信息价值** — §3.5 定义的"fail 时学到什么"
4. **意外发现要详细记录** — 方向的调整往往来自意外观察

## 输入

阅读 `research/problem-statement.md` §3 探针方案，了解：
- §3.1 核心假设
- §3.2 最小实验方案
- §3.3 Pass 标准
- §3.4 时间预算
- §3.5 Fail 时的信息价值

## 探针设计模式

如果 problem-statement.md 的探针方案需要细化，以下是 DL 研究中常用的探针设计模式：

### 1. Synthetic Data Probe（合成数据探针）
**适用场景**：需要精确控制变量，排除数据本身的干扰。
**做法**：构造一个人工数据集，使得你的核心假设是**唯一的区分因素**。
**示例**：如果假设是"长距离依赖是关键"，构造两类序列——一类只需局部信息即可分类，另一类必须看全局。你的方法应该在第二类上显著优于 baseline，在第一类上无显著差异。
**优点**：结果清晰、可重复、不受数据噪声影响。
**陷阱**：合成数据可能过度简化问题，导致在真实数据上不适用。

### 2. Oracle Probe（神谕探针）
**适用场景**：验证 root cause 分析是否正确。
**做法**：假设你的方法的某个关键组件是**完美的**（用 ground truth 替代），看最终效果的 upper bound。
**示例**：如果你认为 root cause 是"attention 分散"，用 ground truth attention mask 替代 learned attention，看性能提升的上界。
**解读**：如果 oracle upper bound 不够高（如 < 5%），说明 root cause 分析可能有误——即使完美解决这个问题也没多大收益。如果上界很高（如 > 20%），说明这个方向有足够的 headroom。

### 3. Scaling Probe（规模探针）
**适用场景**：验证方法的优势是否随问题规模增大而保持/增强。
**做法**：在 2-3 个不同规模上跑同一个实验，观察 scaling behavior。
**示例**：在序列长度 128/512/2048 上分别跑，观察你的方法相对于 baseline 的优势如何变化。
**解读**：如果优势随规模增加而扩大——强信号，方法解决的是 fundamental limitation；如果优势随规模增加而消失——红旗，可能只是在小规模上的偶然优势；如果优势保持不变——需要更多信息判断。

### 4. Ablation Probe（消融探针）
**适用场景**：验证某个特定设计选择的必要性。
**做法**：实现你的核心 idea 的最简版本 + 一个"对照版"（去掉核心 idea，保留其他一切）。
**示例**：如果核心 idea 是"用 frequency domain 替代 spatial domain"，实现一个最简的 FFT-based module 和一个 spatial counterpart，在小数据集上比较。
**注意**：与完整实验中的 ablation 不同，探针 ablation 的目标是验证**核心 idea 是否有 signal**，不需要精确控制所有变量。

### 5. Diagnostic Probe（诊断探针）
**适用场景**：理解现有方法为什么失败。
**做法**：不是测试你的方法，而是**分析现有方法在哪里失败、为什么失败**。
**示例**：对 baseline 的 attention map 做分析，看它在哪些样本上 attention 分散；对 baseline 的错误样本做聚类，找出失败的模式。
**价值**：即使你的探针方法不 work，这类分析也能告诉你 root cause 是否正确。

## 执行流程

1. 按 §3.2 实施最小实验
2. 记录所有定量结果
3. 特别注意意外现象
4. **在时间预算到达 50% 时做中间评估**：结果是否在预期范围内？是否需要调整实验设置？是否已经可以做出判定？

## 如何解读探针结果

### 真信号 vs 噪声的判断

- **真信号的特征**：
  - 效果在多次运行中**一致**（方差小于均值差异）
  - 效果在**不同条件**下保持（如不同随机种子、不同数据子集）
  - 效果的**方向**与理论预测一致（不只是有提升，而且在预期的条件下提升更大）
  - 效果有合理的**效果量**（effect size）——微小但统计显著的提升可能不是有意义的信号

- **可能是噪声/artifact 的特征**：
  - 效果在不同随机种子间**高度不稳定**
  - 效果只在**特定数据子集**上出现（可能是 overfitting）
  - 效果的方向与理论预测**不一致**（如在预期不该有效果的条件下反而有效果）
  - 效果来自**implementation detail** 而非方法本身（如学习率的巧合、初始化的运气）

### 探针失败时的诊断框架

如果探针没有达到 Pass 标准，**不要立即判定方向错误**。按以下框架诊断：

1. **实现问题排查**（最先排除）：
   - 代码有 bug 吗？（检查 gradient flow、检查 loss 是否在下降）
   - 超参合理吗？（试 3-5 组不同超参，看是否有质的变化）
   - 数据处理有问题吗？（检查输入数据的统计特性）

2. **探针设计问题排查**：
   - 探针的任务设计是否真的能测试核心假设？
   - Pass 标准是否设得太高？
   - 实验规模是否太小导致信号被噪声淹没？

3. **方向问题诊断**：
   - Root cause 分析是否准确？（回到 problem-statement.md 重新审视）
   - 攻击角度是否匹配 root cause？（可能 root cause 对但解法错）
   - 是否有更基本的假设不成立？（如数据分布的假设、模型容量的假设）

4. **失败模式分类**：
   - **完全失败**（性能 ≤ random baseline）→ 很可能是方向问题或实现 bug
   - **微弱信号**（有提升但远低于 Pass 标准）→ 可能是方向对但攻击角度不够强
   - **不稳定信号**（有时好有时差）→ 可能需要更 robust 的方法设计
   - **条件性信号**（只在部分条件下有效）→ 需要理解有效/无效条件的区别

## 推进状态

完成后，根据判定推进：

```bash
# 有信号，进入联合设计
python3 ~/Research/Noesis/Praxis/orchestrator/research_runner.py advance <project_path> --outcome signal

# 无信号但问题有价值，换攻击角度
python3 ~/Research/Noesis/Praxis/orchestrator/research_runner.py advance <project_path> --outcome pivot

# 放弃
python3 ~/Research/Noesis/Praxis/orchestrator/research_runner.py advance <project_path> --outcome abandon
```

**判定指南**：
- **signal**：Pass 标准达到，且信号稳定、方向可解释。即使效果不大，只要信号方向正确且稳定，就值得继续
- **pivot**：Pass 标准未达到，但失败诊断指向攻击角度问题（而非 Gap 本身的问题）。换一个攻击角度可能有效
- **abandon**：失败诊断指向 Gap 定义本身有问题（root cause 分析错误），或者问题的 oracle upper bound 太低，不值得继续

# 阶段反思（Phase Reflection）— 自动注入，跨阶段通用

> 此部分由 Runner 在每个非 manual 阶段自动注入，无需手动调用。
> 反思基于你刚才执行的完整工作过程，不是对输出文档的二次审查。

---

## 任务

你刚完成了本阶段的核心工作。现在，**作为执行者**，对这次执行过程做一次简短的批判性反思，将观察追加到 `pipeline-evolution-log.md`。

**核心原则**：反思的价值来自你在执行中的第一手体验——你遇到了什么困难、绕了什么弯路、哪里感觉顺畅、哪里感觉有设计缺陷。这些只有你知道，不能从输出文档中推断。

---

## 反思维度

从以下角度审视本次执行（**没有感触的可跳过**）：

**关于执行流程**
- 有没有步骤让你感到困惑或需要额外判断？prompt 是否覆盖了这种情况？
- 步骤顺序是否合理？有没有你不得不"跳回去"重做的地方？
- 有没有 prompt 强调但实际执行中发现不重要的内容？反之亦然？

**关于输入质量**
- 上游文档是否提供了足够的上下文？有哪些信息缺口影响了执行质量？
- 知识库（Episteme）的相关内容是否充分？跨项目 lessons 是否被有效利用？

**关于输出质量**
- 产出的科学严谨性/写作质量有多大信心？哪些地方仍有不确定性？
- 输出结构（模板格式）是否合适？有什么遗漏或冗余？

**关于审查/编辑阶段（如适用）**
- 标准是否校准合理？有没有对严谨性要求太严或太松？
- Pass / Revise / Block 的边界判定是否清晰？有没有感到犹豫的地方？

---

## 观察分类

将反思整理为以下类别（没有观察的类别可省略）：

| 类别 | 含义 |
|------|------|
| **缺失 (Missing)** | 流程/prompt 中应有但没有的内容 |
| **冗余 (Redundant)** | 有但实际用处不大的内容 |
| **改进 (Improve)** | 现有内容可以做得更好的地方 |
| **确认 (Confirm)** | 执行顺畅、值得保留的设计 |

每条观察标注：
- **影响范围**：`[当前阶段]` 或 `[跨阶段]` 或 `[Prompt: xxx-prompt]`
- **置信度**：`[低]` / `[中]` / `[高]`（单次体验通常为低/中）

---

## 写入 pipeline-evolution-log.md

追加到 `<project_path>/pipeline-evolution-log.md`（文件不存在则新建）：

```markdown
## Entry [序号] — [当前阶段：阶段名称] — [日期]

**执行模式**: [首次 / Revise / Pivot]

### 观察

#### 缺失 (Missing)
- [ ] **[影响范围] [置信度]** — 描述
  - 建议：...

#### 冗余 (Redundant)
- [ ] **[影响范围] [置信度]** — 描述
  - 建议：...

#### 改进 (Improve)
- [ ] **[影响范围] [置信度]** — 描述
  - 建议：...

#### 确认 (Confirm)
- **[影响范围]** — 什么做法有效，为什么
```

**执行要求**：
- 控制在 3-6 条观察，不必面面俱到
- 如果 `pipeline-evolution-log.md` 已有内容，序号递增；如有类似已有条目，引用其编号并注明"再次出现"
- 若发现明显错误（流程矛盾、指令缺失），在条目中标注 `[URGENT]`
- 本步骤**不修改**任何 prompt 文件——只记录观察，正式改进由 `/praxis-evolve` 执行

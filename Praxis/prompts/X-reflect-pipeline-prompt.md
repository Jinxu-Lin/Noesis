# 阶段反思（Phase Reflection）— 自动注入，跨阶段通用

> Runner 在每个非 manual 阶段完成后自动注入。反思基于你的执行过程，不是对输出文档的二次审查。

---

## 任务

你刚完成本阶段核心工作。**作为执行者**，对执行过程做简短批判性反思，追加到 `pipeline-evolution-log.md`。

**核心原则**：反思价值来自执行中的第一手体验——遇到什么困难、绕了什么弯路、哪里顺畅、哪里有设计缺陷。这些不能从输出文档推断。

**深层追问**：不做表层评价，而是质疑阶段的**设计假设**。例如：C 假设 Gap + 攻击角度 + 探针可一次共同设计——成立吗？D 假设方法和实验应同时设计——实际是串行依赖的吗？

---

## 反思维度（没有感触的跳过）

**执行流程**
- 有无步骤让你困惑或需额外判断？prompt 是否覆盖？
- 步骤顺序合理吗？有无不得不"跳回"重做的地方？
- prompt 强调但实际不重要的内容？反之亦然？

**时间与精力分配**
- 最耗时步骤是什么？分配合理吗？
- 有无思考深度远超 prompt 暗示的步骤？
- 有无 prompt 写得长但执行起来是机械性的步骤？

**输入质量**
- 上游文档是否提供足够上下文？哪些信息缺口影响了质量？
- Episteme 内容是否充分？跨项目 lessons 是否被有效利用？
- 上游文档格式是否便于提取关键信息？

**输出质量**
- 对产出的科学严谨性/写作质量有多大信心？哪里仍有不确定性？
- 输出结构是否合适？有无遗漏或冗余？
- 输出是否充分考虑下游阶段需求？

**阶段边界**
- 范围是否合理？有无边界不清——不确定该在本阶段做还是留给下游？
- 阶段间信息传递是否充分？有无上游缺失或下游用不到的信息？

**审查/编辑阶段（如适用）**
- 标准校准合理吗？对严谨性要求太严或太松？
- Pass / Revise / Block 边界判定是否清晰？

## 观察分类

| 类别 | 含义 |
|------|------|
| **缺失 (Missing)** | 流程/prompt 中应有但没有的 |
| **冗余 (Redundant)** | 有但实际用处不大的 |
| **改进 (Improve)** | 现有内容可做得更好的 |
| **确认 (Confirm)** | 执行顺畅、值得保留的设计 |
| **边界 (Boundary)** | 阶段边界或信息传递问题 |

每条标注：
- **影响范围**：`[当前阶段]` / `[跨阶段]` / `[Prompt: xxx-prompt]`
- **置信度**：`[低]` / `[中]` / `[高]`

## 写入 pipeline-evolution-log.md

追加到 `<project_path>/pipeline-evolution-log.md`（不存在则新建）：

```markdown
## Entry [序号] — [当前阶段名称] — [日期]

**执行模式**: [首次 / Revise / Pivot]
**时间分配**: [最耗时步骤及占比]

### 观察

#### 缺失 (Missing)
- [ ] **[影响范围] [置信度]** — 描述
  - 建议：...

#### 改进 (Improve)
- [ ] **[影响范围] [置信度]** — 描述
  - 建议：...

#### 边界 (Boundary)
- [ ] **[影响范围] [置信度]** — 描述
  - 建议：...

#### 确认 (Confirm)
- **[影响范围]** — 什么做法有效，为什么
```

**要求**：
- 控制在 3-6 条，不必面面俱到
- 序号递增；类似已有条目引用其编号并注明"再次出现"
- 明显错误（流程矛盾、指令缺失）标注 `[URGENT]`
- 阶段边界问题标注 `[BOUNDARY]`
- **不修改**任何 prompt 文件——只记录观察，正式改进由 `/praxis-evolve` 执行
